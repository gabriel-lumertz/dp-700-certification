Você entende o padrão de medalhão , agora vamos torná-lo concreto em Fabric. Três decisões definem sua implementação: como o lakehouse é estruturado, quais ferramentas movem os dados entre as camadas e como a camada gold é disponibilizada aos consumidores.

## Estruturar sua casa no lago

Você pode usar uma única casa de lago para todas as três camadas ou dar a cada camada sua própria casa de lago ou até mesmo seu próprio workspace. A desvantagem é entre simplicidade e isolamento.

|Opção|Melhor para|
|---|---|
|Lakehouse única com esquemas|Mais simples de gerenciar; bom para equipes menores ou projetos em estágio inicial|
|Casas de lago separadas|Separação mais clara; aplicar permissões diferentes por camada|
|Espaços de trabalho separados|Isolamento mais forte; necessário para cenários regulatórios ou de conformidade|

Em um lakehouse, **esquemas** ajudam a manter a organização. Os esquemas são habilitados por padrão quando você cria um lakehouse no Fabric. A criação de esquemas denominados `bronze`, `silver`e `gold` mantém tabelas agrupadas por camada, torna-as mais fáceis de descobrir e permite que você defina diferentes permissões de acesso por camada , sem a sobrecarga de gerenciar casas de lago separadas.

## A camada de bronze

A camada bronze é sua zona de destino de dados brutos. Os dados chegam aqui exatamente como vieram da origem – sem alterações, sem limpeza. Isso é intencional: se uma transformação der errado mais adiante no pipeline, você sempre poderá reprocessar a partir da camada bronze em vez de voltar ao sistema de origem.

A forma como você leva os dados para a camada bronze depende de onde eles estão. Se sua origem já estiver no armazenamento em nuvem — OneLake, Azure Data Lake Storage Gen2, Amazon S3 ou Google Cloud Storage — use um atalho do OneLake para referenciá-lo no local sem copiar. Os atalhos mantêm sua camada bronze sincronizada com a origem automaticamente, sem código de pipeline nem de ingestão. Para outras fontes, use pipelines, fluxos de dados ou notebooks para carregar dados na camada bronze.

## A camada de prata

A camada de prata é onde os dados são limpos e integrados. As transformações aqui se concentram na qualidade e na consistência — padronizando formatos, removendo valores nulos, eliminando registros duplicados e unindo dados de várias fontes da camada bronze em um conjunto de dados unificado. A meta é um conjunto de dados confiável e integrado que analistas e cientistas de dados podem usar diretamente.

Fabric oferece três maneiras de fazer isso:

**Os fluxos de dados (Gen2)** são uma opção de baixo código. Elas funcionam bem para transformações simples – filtragem, renomeação de colunas, alteração de tipos de dados – sem escrever código.

**Os notebooks** oferecem controle total usando Python ou SQL. Elas são a escolha certa para grandes conjuntos de dados, lógica complexa ou qualquer coisa que um fluxo de dados não possa lidar : cálculos personalizados, chamadas à API ou junções complexas.

**Visualizações materializadas do lake** permitem definir uma transformação em SQL. Você escreve uma consulta que descreve como sua tabela silver deve ser, e o Fabric a cria e salva para você.

Por exemplo, essa exibição cria uma tabela limpa `sales` na camada prata selecionando entre bronze, padronizando formatos e filtrando linhas com uma ID de pedido ausente:

SQL

```
CREATE MATERIALIZED LAKE VIEW silver.sales
AS
SELECT
    order_id,
    customer_id,
    UPPER(TRIM(region))        AS region,
    CAST(order_date AS DATE)   AS order_date,
    unit_price * quantity      AS total_amount
FROM bronze.sales
WHERE order_id IS NOT NULL
```

A principal diferença em relação a uma view SQL comum: uma view comum executa novamente sua consulta sempre que alguém a consulta. Uma exibição materializada do lago salva os resultados como uma tabela real. Quando novos dados chegam em bronze, o Fabric atualiza apenas as linhas que foram alteradas — ele não reprocessa a tabela inteira. A tabela permanece atual automaticamente; você não precisa agendar nem disparar nada. Isso funciona porque todas as tabelas Fabric são armazenadas no formato Delta, que acompanha cada alteração conforme ela acontece. Quando novas linhas chegam em bronze, Fabric verifica esse log e atualiza apenas as novas linhas em prata.

A desvantagem: sua transformação precisa poder ser expressa em SQL. Se você precisar de lógica em Python, use um notebook.

## A camada de ouro

A camada gold é onde os dados são estruturados para consumo pelo negócio. Um padrão comum é modelá-lo como um **esquema em estrela** — tabelas de fatos rodeadas por tabelas de dimensão, agregadas no nível de granularidade necessário para relatórios. Mas o formato depende de quem vai consumi-lo: uma equipe de ciência de dados pode querer uma tabela desnormalizada e ampla, otimizada para engenharia de atributos, enquanto uma equipe financeira pode querer resumos pré-agregados. Você pode ter várias camadas de ouro que atendem a públicos diferentes , os mesmos dados de prata abaixo, cada camada de ouro modelada de forma diferente para as necessidades de cada equipe.

Você cria a camada de ouro usando as mesmas ferramentas da camada prata: fluxos de dados, notebooks ou exibições materializadas do lake, orquestradas por pipelines.

Os consumidores acessam a camada gold por meio do **endpoint de análise SQL** (consultas T-SQL diretas nas tabelas Delta) ou de um **modelo semântico do Power BI** (uma camada voltada para os negócios, com medidas e terminologia predefinidas). Se sua equipe trabalha principalmente no SQL, um **Fabric Data Warehouse** pode servir como a camada de ouro em vez de uma casa no lago.
