Entender como escrever consultas KQL eficientes é essencial para obter um bom desempenho ao trabalhar com Eventhouses. Nesta unidade, abordamos as principais técnicas de otimização e explicamos por que são importantes para suas consultas.

## Por que a otimização de consultas é importante

O desempenho da consulta em bancos de dados KQL depende do volume de dados processados. Quando você entende como o KQL processa os dados, é possível escrever consultas que:

- **São executadas com mais rapidez**, reduzindo os dados verificados. Por exemplo, em vez de verificar milhões de linhas, aplique um filtro com antecedência para processar apenas milhares
- **Usam menos recursos**: por exemplo, selecionar apenas 3 colunas em vez de todas as 50 colunas reduz a sobrecarga de processamento
- **Trabalham de modo confiável com os dados crescentes**: por exemplo, uma consulta que trabalha em 1 milhão de linhas hoje ainda terá um bom desempenho quando seus dados aumentarem para 10 milhões de linhas

O princípio fundamental é: quanto menos dados sua consulta precisar processar, mais rápido ela será executada.

## Entender as principais técnicas de otimização

### Filtrar dados com antecedência e efetivamente

A filtragem reduz a quantidade de dados que as operações subsequentes precisam processar e os bancos de dados KQL usam índices e técnicas de organização de dados que tornam a filtragem antecipada especialmente eficiente.

**A filtragem baseada em tempo** é eficaz porque os Eventhouses normalmente contêm dados de série temporal:

kql

```
TaxiTrips
| where pickup_datetime > ago(30min)  // Filter first - uses time index
| project trip_id, vendor_id, pickup_datetime, fare_amount
| summarize avg_fare = avg(fare_amount) by vendor_id
```

**Ordenar os filtros pelo volume de dados que eles eliminam**: coloque filtros que eliminam a maioria dos dados primeiro. Pense nele como um funil: comece com o filtro que remove a maioria das linhas e aplique filtros mais específicos aos dados restantes:

kql

```
TaxiTrips
| where pickup_datetime > ago(1d)    // Time filter first - eliminates most data
| where vendor_id == "VTS"           // Specific vendor - eliminates some data  
| where fare_amount > 0              // Value filter - eliminates least data
| summarize trip_count = count()
```

### Reduzir as colunas com antecedência

_Projetar_ ou selecionar apenas as colunas necessárias reduz o uso de recursos. Isso é especialmente importante ao trabalhar com tabelas largas que têm muitas colunas.

kql

```
TaxiTrips
| project trip_id, pickup_datetime, fare_amount  // Select columns early
| where pickup_datetime > ago(1d)                // Then filter
| summarize avg_fare = avg(fare_amount)
```

### Otimizar agregações e junções

Agregações e junções são operações com uso intensivo de recursos porque precisam processar e combinar grandes quantidades de dados. O modo como você os estrutura pode afetar consideravelmente o desempenho da consulta.

**Para agregações, limite os resultados ao explorar os dados**:

kql

```
TaxiTrips
| where pickup_datetime > ago(1d)
| summarize trip_count = count() by trip_id, vendor_id
| limit 1000  // Limit results for exploration
```

**Para junções, coloque a tabela menor em primeiro lugar**. Ao unir tabelas, o KQL processa a primeira tabela que corresponda à segunda tabela. Começar com uma tabela menor significa menos linhas a serem processadas, tornando a junção mais eficiente.

kql

```
// Good: Small vendor table first
VendorInfo        
| join kind=inner TaxiTrips on vendor_id

// Avoid: Large taxi table first
TaxiTrips         
| join kind=inner VendorInfo on vendor_id
```
