Sem modelagem de dados, cada consumer precisa descobrir quais tabelas se relacionam entre si, escrever sua própria lógica de agregação e adivinhar os significados da coluna. A modelagem de dados resolve esse problema inserindo estrutura, lógica de negócios e documentação diretamente no warehouse. Em um Microsoft Fabric warehouse, você prepara dados para claridade, define relações entre tabelas, padroniza o acesso por meio de visões e medidas e publica modelos semânticos para os relatórios. Essas opções de modelagem afetam todas as experiências downstream, incluindo consultas T-SQL, relatórios do Power BI e análise de linguagem natural orientada por IA.

## Preparar dados para consumo

Antes de definir relações ou adicionar cálculos, você precisa limpar o que os consumidores veem. As tabelas brutas do armazém de dados geralmente contêm tabelas de preparo, colunas de chaves alternativas e sinalizadores internos destinados ao processamento de ETL, não para análise. Esses objetos criam ruído quando os consumidores navegam pelos dados. Preparar o armazém para consumo significa mostrar apenas o que é relevante e torná-lo compreensível.

No modo de exibição de modelo, você pode executar várias etapas para melhorar a experiência do consumidor:

- **Oculte objetos internos** como tabelas de preparo, colunas de chaves alternativas e artefatos de ETL que poluem a lista de campos.
- **Renomeie colunas** para usar nomes relacionados aos negócios em que os nomes das colunas do armazém são técnicos ou abreviados. Por exemplo, renomeie `CustRgn` para `Customer Region`.
- **Adicione descrições a tabelas** e colunas para que os consumidores entendam o que os dados representam sem se referir à documentação externa.

Essas etapas importam além da arrumação. Os agentes de dados Copilot no Power BI e no Fabric IQ dependem de nomes de tabela, nomes de coluna e descrições para interpretar questões de linguagem natural e gerar DAX ou SQL precisos. Uma coluna nomeada `Customer Region` com uma descrição como "Região geográfica do endereço primário do cliente" produz melhores resultados de linguagem natural do que `CustRgn` sem descrição.

Com tabelas limpas e bem nomeadas, você está pronto para definir como essas tabelas se conectam umas às outras.

## Entender as relações entre tabelas

Uma relação é uma conexão lógica entre duas tabelas que permite filtragem, agrupamento e agregação entre essas tabelas. Em um esquema de estrela, as relações conectam tabelas de fatos a tabelas de dimensão por meio de colunas de chave compartilhadas.

Por exemplo, uma `CustomerKey` coluna que existe em ambos `FactSales` e `DimCustomer` estabelece o link que permite a análise de vendas por atributos do cliente, como região, segmento ou tipo de conta.

Cada relação tem duas propriedades importantes.

- **Cardinalidade** descreve como as linhas nas duas tabelas correspondem. Em um esquema de estrela, as relações fato-para-dimensão normalmente são muitos-para-um, o que significa que muitas linhas de fatos são mapeadas para uma única linha de dimensão.
- **A direção de filtragem cruzada** determina de que forma os filtros se propagam entre as tabelas. A direção única, em que a dimensão filtra a tabela de fatos, é a configuração padrão para a maioria dos designs de esquema de estrela porque mantém o comportamento do filtro previsível e com desempenho.

Sem relações definidas, cada consumidor que deseja combinar dados entre tabelas precisa escrever uma lógica JOIN explícita. As relações eliminam essa repetição codificando a conexão uma vez. Quando você cria um modelo semântico do warehouse, essas relações informam como agentes de dados do Power BI, Copilot e Fabric IQ interpretam os dados. Os agentes de dados, por exemplo, usam relações para gerar junções precisas ao traduzir perguntas de linguagem natural para o SQL.

> [!Observação]
> 
> 
> A maioria dos data warehouses usa modelagem dimensional. As relações podem ser criadas para moldar um **esquema de estrela**, que é um modelo ideal para análise. Para obter mais informações, consulte o módulo [Design de modelos dimensionais no Microsoft Fabric](https://learn.microsoft.com/pt-br/training/modules/design-dimensional-models-fabric).

## Padronizar o acesso a dados com visões e medidas

Agora que suas tabelas estão limpas e conectadas, a próxima etapa é fornecer aos consumidores maneiras confiáveis e consistentes de consultar e calcular em relação a esses dados. Sem padronização, cada equipe grava sua própria lógica de junção, aplica seus próprios filtros e define suas próprias fórmulas, o que leva a resultados conflitantes.

**Views** fornecem essa consistência para os consumidores T-SQL. Uma exibição encapsula a lógica de junção, filtros e seleções de coluna em uma consulta reutilizável que os consumidores referenciam como uma tabela. Por exemplo, uma vista que une tabelas de fatos e dimensões, filtra os pedidos concluídos e apresenta somente as colunas necessárias para os analistas fornece a cada consumidor T-SQL uma base confiável. As visualizações também servem como fontes de dados estáveis para relatórios. Em vez de criar relatórios diretamente em tabelas base que podem ser alteradas, você pode apontar relatórios para exibições que apresentam uma forma consistente.

**As medidas** fornecem a mesma consistência para cálculos DAX. Uma medida é uma expressão DAX reutilizável que define um cálculo como total, média, taxa ou contagem. Você cria medidas diretamente no modo de exibição de modelo de warehouse selecionando uma tabela e adicionando uma nova medida. Por exemplo, uma `Total Sales` medida que soma a `SalesAmount` coluna garante que cada consumidor use o mesmo cálculo.

Como a definição de medida reside nos dados, ela se torna a única fonte de verdade para essa métrica. Quando a empresa altera a forma como calcula a receita, você atualiza a medida em um só lugar, em vez de rastrear cada relatório que contém sua própria fórmula.

Juntos, as visões e medidas abrangem ambos os lados do consumo: as visões padronizam como os consumidores de T-SQL acessam e consultam os dados, enquanto as medidas padronizam como os cálculos empresariais aparecem em relatórios e painéis.

> [!Dica]
> 
> 
> Fórmulas DAX e design de medidas avançadas são abordados detalhadamente em módulos posteriores. Para ver exibições e procedimentos armazenados, consulte a unidade anterior sobre como consultar e transformar dados.

## Criar um modelo semântico para relatórios do Power BI

Com tabelas preparadas, relações definidas e exibições e medidas padronizadas em uso, o armazém está pronto para relatórios subsequentes. As equipes que consultam o armazém diretamente usando o T-SQL ou se conectam por meio de ferramentas de terceiros podem trabalhar com o modelo de warehouse as-is. No entanto, quando você deseja criar dashboards e relatórios interativos do Power BI, criar um modelo semântico é a próxima etapa.

Modelos semânticos criados a partir de um armazém de malha usam o modo Direct Lake. Ao contrário do modo de importação tradicional, que copia dados na memória do Power BI, o Direct Lake lê dados diretamente dos arquivos do OneLake Parquet. Isso significa que os relatórios refletem os dados mais recentes do warehouse sem a necessidade de atualizações agendadas. Isso também significa que você evita o armazenamento e a sobrecarga de processamento ao manter uma cópia separada dos dados.
