No Microsoft Fabric, existem muitas maneiras de escolher carregar dados em um warehouse. Essa etapa é fundamental, pois garante que os dados de alta qualidade, transformados ou processados sejam integrados em apenas um repositório.

Além disso, a eficiência do carregamento de dados afeta diretamente a pontualidade e a precisão da análise, tornando-a vital para os processos de tomada de decisão em tempo real. Investir tempo e recursos projetando e implementando uma estratégia robusta de carregamento de dados é essencial para o êxito do projeto de data warehouse.

## Entenda as operações de ingestão de dados e de carregamento de dados

Embora ambos os processos façam parte do pipeline ETL (Extrair, Transformar, Carregar) em um cenário de data warehouse, eles geralmente são fornecidos para finalidades diferentes. **A extração/ingestão de dados** consiste em mover dados brutos de várias fontes para um repositório central. Por outro lado, o **carregamento de dados** envolve pegar os dados transformados ou processados e carregá-los no destino final de armazenamento para análise e relatórios.

Data warehouses de malha e lakehouses armazenam automaticamente seus dados no OneLake usando o formato Delta Parquet.

## Prepare seus dados

Talvez você tenha que criar e trabalhar com objetos auxiliares envolvidos em uma operação de carregamento, como tabelas, procedimentos armazenados e funções. Esses objetos auxiliares são normalmente referenciados como **preparo**. Os objetos de preparo atuam como armazenamento temporário e áreas de transformação. Eles podem compartilhar recursos com um data warehouse ou residir em uma área de armazenamento própria.

O processo de preparo é fornecido como uma camada de abstração, simplificando e facilitando a operação de carregamento para as tabelas finais no data warehouse.

![Diagrama de etapas sequenciais no processo de ciência de dados.](https://learn.microsoft.com/pt-br/training/wwl-data-ai/load-data-into-microsoft-fabric-data-warehouse/media/1-data-warehouse-process.png)

Além disso, a área de preparo fornece um buffer que pode ajudar a minimizar o impacto da operação de carga no desempenho do data warehouse. Isso é importante em ambientes nos quais o data warehouse precisa permanecer operacional e responsivo durante o processo de carregamento de dados.

## Examine os tipos de cargas de dados

Existem dois tipos de cargas de dados que devem ser considerados ao carregar um data warehouse.

|Tipo de Carga|Descrição|Operação|Duração|Complexidade|Melhor utilizado|
|---|---|---|---|---|---|
|**Carga completa (inicial)**|O processo de preenchimento do data warehouse pela primeira vez.|Todas as tabelas são truncadas e recarregadas, e os dados antigos são perdidos|Pode levar mais tempo para ser concluído devido à quantidade de dados que está sendo tratada|Mais fácil de implementar, pois não existe histórico preservado|Esse método é normalmente usado ao configurar um novo data warehouse ou quando é necessária uma atualização completa dos dados|
|**Carga incremental**|O processo de atualização do data warehouse com as alterações desde a última atualização|O histórico é preservado e as tabelas são atualizadas com novas informações|Leva menos tempo que o carregamento inicial|A implementação é mais complexa do que a carga inicial|Esse método é normalmente utilizado para atualizações regulares do data warehouse, como atualizações diárias ou horárias. Requer mecanismos para acompanhar as alterações nos dados de origem desde a última carga.|

Um processo de ETL (Extrair, Transformar, Carregar) para um data warehouse nem sempre precisa tanto da carga completa quanto da carga incremental. Em alguns casos, pode ser usada uma combinação dos dois métodos. A escolha entre uma carga completa e uma carga incremental depende de muitos fatores, como a quantidade de dados, as características dos dados e os requisitos do data warehouse.

Para obter mais informações sobre como executar uma carga incremental, confira [**Carga incremental**](https://learn.microsoft.com/pt-br/fabric/data-factory/tutorial-incremental-copy-data-warehouse-lakehouse).

## Entender a chave de negócios e a chave substituta

Em um data warehouse, as chaves substitutas e as chaves de negócios são essenciais para a efetiva integração de dados e armazenamento de dados, mas elas servem a diferentes finalidades.

- **Chave substituta:** Uma chave alternativa é um identificador gerado pelo sistema que é usado para identificar de maneira exclusiva um registro em uma tabela dentro do data warehouse. Ele não tem nenhum significado comercial e normalmente é um inteiro ou um identificador exclusivo. Chaves substitutas são usadas para manter a consistência e a precisão no data warehouse, especialmente ao integrar dados de várias fontes. Eles ajudam a evitar problemas que podem surgir de alterações nos sistemas de origem, como reutilização ou alteração de chaves de negócios.
- **Chave de negócios:** Uma chave de negócios, também conhecida como chave natural, é um identificador que vem do sistema de origem e tem significado comercial. Ele é usado para identificar exclusivamente um registro no sistema de origem. Exemplos de chaves de negócios incluem códigos de produto, IDs de cliente e números de funcionários. As chaves de negócios são importantes para manter a rastreabilidade entre o data warehouse e os sistemas de origem. Elas ajudam a garantir que os dados no warehouse possam ser correspondidos com precisão aos registros correspondentes nos sistemas de origem.

## Carregar uma tabela de dimensões

Pense em uma tabela de dimensões como o _"quem, o quê, onde, quando, por quê"_ do seu data warehouse. Ela é como o pano de fundo descritivo que fornece contexto aos números brutos encontrados nas tabelas de fatos.

Por exemplo, se estiver executando um repositório online, sua tabela de fatos poderá conter os dados brutos de vendas, quantas unidades de cada produto foram vendidas. Mas, sem uma tabela de dimensões, você não saberia quem comprou esses produtos, quando eles foram comprados ou em que local o comprador está localizado.

### Dimensões de variáveis lentas (SCD)

As Dimensões Variáveis Lentas evoluem com o tempo, mas em um ritmo lento e imprevisível. Por exemplo, o endereço de um cliente em um negócio de varejo. Quando um cliente se muda, o endereço dele é alterado. Se você sobrescrever o endereço antigo com o novo, você perderá os dados históricos. No entanto, se você precisar analisar dados históricos de vendas, é crucial saber onde o cliente morava no momento de cada venda. É aqui que os SCDs se tornam essenciais.

Existem vários tipos de dimensões variáveis lentas em um data warehouse, sendo que o tipo 1 e o tipo 2 são os mais usados.

- **Type 0 SCD:** Os atributos da dimensão nunca são alterados.
- **Type 1 SCD**: Substitui os dados existentes, não mantém o histórico.
- **Type 2 SCD**: Adiciona novos registros para alterações, mantém o histórico completo para uma determinada chave natural.
- **Type 3 SCD:** O histórico é adicionado como uma nova coluna.
- **Type 4 SCD**: Uma nova dimensão é adicionada.
- **Type 5 SCD**: Quando determinados atributos de uma dimensão grande são alterados com o tempo, mas o uso do tipo 2 não é viável devido ao tamanho grande da dimensão.
- **Type 6 SCD**: Combinação do tipo 2 e do tipo 3.

No SCD tipo 2, quando uma nova versão do mesmo elemento é trazida para o data warehouse, a versão antiga é considerada expirada e a nova se torna ativa.

[![Diagrama mostrando a função e a estrutura do OneLake.](https://learn.microsoft.com/pt-br/training/wwl-data-ai/load-data-into-microsoft-fabric-data-warehouse/media/2-slowly-changing-dimension.png)](https://learn.microsoft.com/pt-br/training/wwl-data-ai/load-data-into-microsoft-fabric-data-warehouse/media/2-slowly-changing-dimension.png#lightbox)

O código a seguir mostra um exemplo simples sobre como lidar com a chave de negócios em um SCD tipo 2 para a tabela _Dim_Products_ usando T-SQL.

SQL

```
IF EXISTS (SELECT 1 FROM Dim_Products WHERE SourceKey = @ProductID AND IsActive = 'True')
BEGIN
    -- Existing product record
    UPDATE Dim_Products
    SET ValidTo = GETDATE(), IsActive = 'False'
    WHERE SourceKey = @ProductID 
        AND IsActive = 'True';
END
ELSE
BEGIN
    -- New product record
    INSERT INTO Dim_Products (SourceKey, ProductName, StartDate, EndDate, IsActive)
    VALUES (@ProductID, @ProductName, GETDATE(), '9999-12-31', 'True');
END
```

O mecanismo de detecção de alterações nos sistemas de origem é crucial para determinar quando os registros são inseridos, atualizados ou excluídos. [A Captura de Dados de Alterações (CDA)](https://learn.microsoft.com/pt-br/sql/relational-databases/track-changes/about-change-data-capture-sql-server), o [controle de alterações](https://learn.microsoft.com/pt-br/sql/relational-databases/track-changes/about-change-tracking-sql-server) e os [gatilhos](https://learn.microsoft.com/pt-br/sql/relational-databases/triggers/dml-triggers) são os recursos disponíveis para gerenciar o acompanhamento de dados em sistemas de origem, como o SQL Server.

## Carregar uma tabela de fatos

Normalmente, uma operação de carga de data warehouse padrão envolve o carregamento de tabelas de fatos após tabelas de dimensão. Isso garante que as dimensões às quais os fatos fazem referência já estejam presentes no data warehouse.

Os dados de fatos preparados geralmente incluem as chaves de negócios para as dimensões relacionadas, portanto, sua lógica para carregar os dados precisa procurar as chaves alternativas correspondentes. Ao lidar com dimensões de alteração lenta no data warehouse, é crucial identificar a versão apropriada do registro de dimensão para garantir que a chave alternativa correta seja usada. Isso corresponde ao evento registrado na tabela de fatos com o estado da dimensão no momento em que o fato ocorreu.

Em muitos casos, você pode recuperar a versão "atual" mais recente da dimensão. No entanto, às vezes, talvez seja necessário encontrar o registro de dimensão correto com base em colunas DateTime que indicam o período de validade para cada versão da dimensão.

O exemplo a seguir pressupõe que os registros de dimensão tenham uma chave alternativa incremental e que a versão adicionada mais recentemente de uma instância de dimensão específica, que terá o valor de chave mais alto, poderá ser usada.

SQL

```
-- Lookup keys in dimension tables
INSERT INTO dbo.FactSales
SELECT  (SELECT MAX(DateKey)
         FROM dbo.DimDate
         WHERE FullDateAlternateKey = stg.OrderDate) AS OrderDateKey,
        (SELECT MAX(CustomerKey)
         FROM dbo.DimCustomer
         WHERE CustomerAlternateKey = stg.CustNo) AS CustomerKey,
        (SELECT MAX(ProductKey)
         FROM dbo.DimProduct
         WHERE ProductAlternateKey = stg.ProductID) AS ProductKey,
        (SELECT MAX(StoreKey)
         FROM dbo.DimStore
         WHERE StoreAlternateKey = stg.StoreID) AS StoreKey,
        OrderNumber,
        OrderLineItem,
        OrderQuantity,
        UnitPrice,
        Discount,
        Tax,
        SalesAmount
FROM dbo.StageSales AS stg
```
