Depois que as tabelas de dimensão e fatos em um data warehouse forem preenchidas com dados, você poderá usar o T-SQL para consultá-las e analisá-las. O T-SQL dá suporte `SELECT`, `JOIN`funções de agregação, funções de janela e muito mais, oferecendo as ferramentas para extrair, filtrar, agrupar e resumir seus dados.

## Agregar medidas por atributos de dimensão

Um padrão comum é unir uma tabela de fatos a uma ou mais tabelas de dimensão e, em seguida, agregar uma medida numérica agrupada por um atributo de dimensão.

A consulta a seguir agrega os valores de vendas por ano e trimestre das **tabelas FactSales** e **DimDate** :

SQL

```
SELECT  dates.CalendarYear,
        dates.CalendarQuarter,
        SUM(sales.SalesAmount) AS TotalSales
FROM dbo.FactSales AS sales
JOIN dbo.DimDate AS dates ON sales.OrderDateKey = dates.DateKey
GROUP BY dates.CalendarYear, dates.CalendarQuarter
ORDER BY dates.CalendarYear, dates.CalendarQuarter;
```

Os resultados são semelhantes à tabela a seguir:

|---|---|---|
|2024|1|25980.16|
|2024|2|27453.87|
|2024|3|28527.15|
|2024|4|31083.45|
|2025|1|34562.96|
|2025|2|36162.27|
|...|...|...|

Você pode unir várias tabelas de dimensão para fatiar os resultados por atributos adicionais. A consulta a seguir estende o exemplo anterior para dividir as vendas trimestrais por cidade, usando a tabela **DimCustomer** :

SQL

```
SELECT  dates.CalendarYear,
        dates.CalendarQuarter,
        custs.City,

FROM dbo.FactSales AS sales
JOIN dbo.DimDate AS dates ON sales.OrderDateKey = dates.DateKey
JOIN dbo.DimCustomer AS custs ON sales.CustomerKey = custs.CustomerKey
GROUP BY dates.CalendarYear, dates.CalendarQuarter, custs.City
ORDER BY dates.CalendarYear, dates.CalendarQuarter, custs.City;
```

### Junções em um esquema floco de neve

Ao usar um esquema em floco de neve, as dimensões podem ser parcialmente normalizadas, exigindo que várias junções relacionem tabelas de fatos a dimensões do esquema em floco de neve. Por exemplo, suponha que o data warehouse inclui uma tabela de dimensões **DimProduct** da qual as categorias de produto foram normalizadas em uma tabela **DimCategory** separada. Uma consulta para agregar itens vendidos por categoria de produto pode ser semelhante ao seguinte exemplo:

SQL

```
SELECT  cat.ProductCategory,
        SUM(sales.OrderQuantity) AS ItemsSold
FROM dbo.FactSales AS sales
JOIN dbo.DimProduct AS prod ON sales.ProductKey = prod.ProductKey
JOIN dbo.DimCategory AS cat ON prod.CategoryKey = cat.CategoryKey
GROUP BY cat.ProductCategory
ORDER BY cat.ProductCategory;
```

Os resultados dessa consulta incluem o número de itens vendidos para cada categoria de produto:

|ProductCategory|ItemsSold|
|---|---|
|Accessories|28271|
|Roupas|5368|
|...|...|

> [!Observação]
> 
> 
> Ambas as `JOIN` cláusulas são necessárias para atravessar a cadeia de relações de **FactSales** para **DimCategory** por meio de **DimProduct**, embora nenhum campo de **DimProduct** apareça nos resultados.

## Usando funções de classificação

Outra consulta analítica comum particiona resultados por um atributo de dimensão e as classifica dentro de cada partição. Por exemplo, talvez você queira classificar as lojas a cada ano pela receita de vendas. Para atingir essa meta, você pode usar funções de _classificação_ Transact-SQL, como `ROW_NUMBER`, `RANK`, `DENSE_RANK` e `NTILE`. Essas funções permitem particionar dados entre categorias, cada uma retornando um valor que indica a posição relativa de cada linha dentro da partição:

- **ROW_NUMBER** retorna a posição ordinal da linha dentro da partição. Por exemplo, a primeira linha é numerada como 1, a segunda como 2 e assim por diante.
- **RANK** retorna a posição classificada de cada linha nos resultados ordenados. Por exemplo, em uma partição de lojas ordenadas pelo volume de vendas, a loja com o maior volume de vendas é classificada como 1. Se várias lojas tiverem os mesmos volumes de vendas, elas serão classificadas da mesma forma, e a classificação atribuída às lojas seguintes refletirá o número de lojas que têm volumes de vendas mais altos – incluindo empates.
- **DENSE_RANK** classifica linhas em uma partição da mesma maneira que **RANK**, mas quando várias linhas têm a mesma classificação, as linhas subsequentes são classificadas sem lacunas — os laços não consomem posições extras.
- **NTILE** retorna o percentil especificado em que a linha se enquadra. Por exemplo, em uma partição de lojas ordenadas pelo volume de vendas, `NTILE(4)` retorna o quartil em que o volume de vendas de uma loja a coloca.

Por exemplo, considere a seguinte consulta:

SQL

```
SELECT  ProductCategory,
        ProductName,
        ListPrice,
        ROW_NUMBER() OVER
            (PARTITION BY ProductCategory ORDER BY ListPrice DESC) AS RowNumber,
        RANK() OVER
            (PARTITION BY ProductCategory ORDER BY ListPrice DESC) AS Rank,
        DENSE_RANK() OVER
            (PARTITION BY ProductCategory ORDER BY ListPrice DESC) AS DenseRank,
        NTILE(4) OVER
            (PARTITION BY ProductCategory ORDER BY ListPrice DESC) AS Quartile
FROM dbo.DimProduct
ORDER BY ProductCategory;
```

A consulta particiona produtos por categoria, classificando cada produto dentro de sua partição por preço de lista. Os resultados são semelhantes à tabela a seguir:

|ProductCategory|ProductName|ListPrice|RowNumber|Classificação|DenseRank|Quartile|
|---|---|---|---|---|---|---|
|Accessories|Garrafa de água|8,99|1|1|1|1|
|Accessories|Tiara|8,49|2|2|2|1|
|Accessories|Aquecedores de braço|5,99|3|3|3|2|
|Accessories|Tornozeleira|5,99|4|3|3|2|
|Accessories|Palmilha|2,99|5|5|4|3|
|Accessories|Cadarço|0,25|6|6|5|4|
|Roupas|Boné de corrida|7,49|1|1|1|1|
|Roupas|Manga de Compactação|6,99|2|2|2|1|
|Roupas|Mochila de ginástica|4.25|3|3|3|2|
|...|...|...|...|...|...|...|

> [!Observação]
> 
> 
> Os resultados de exemplo demonstram a diferença entre `RANK` e `DENSE_RANK`. Observe que, na categoria _Acessórios_ , os produtos _Arm Warmers_ e _Ankle Strap_ têm o mesmo preço de lista e são classificados como o 3º produto com preços mais altos. O próximo produto com preço mais alto tem um _RANK_ de 5 (há quatro produtos mais caros do que ele) e um _DENSE_RANK_ de 4 (há três preços mais altos).

Para saber mais sobre as funções de classificação, consulte o módulo [Usar funções internas e GROUP BY no Transact-SQL](https://learn.microsoft.com/pt-br/sql/t-sql/functions/ranking-functions-transact-sql).

## Recuperando uma contagem aproximada

Embora a finalidade de um data warehouse seja principalmente dar suporte a modelos de dados analíticos e relatórios para a empresa, analistas de dados e cientistas de dados geralmente precisam executar alguma exploração inicial de dados para determinar a escala e a distribuição básicas dos dados.

Por exemplo, a consulta a seguir usa a `COUNT` função para recuperar o número de vendas para cada ano:

SQL

```
SELECT dates.CalendarYear AS CalendarYear,
    COUNT(DISTINCT sales.OrderNumber) AS Orders
FROM FactSales AS sales
JOIN DimDate AS dates ON sales.OrderDateKey = dates.DateKey
GROUP BY dates.CalendarYear
ORDER BY CalendarYear;
```

Os resultados dessa consulta podem ser semelhantes à seguinte tabela:

|CalendarYear|Pedidos|
|---|---|
|2023|239870|
|2024|284741|
|2025|309272|
|...|...|

O volume de dados em um data warehouse pode significar que até mesmo consultas simples para contar o número de registros que atendem aos critérios especificados levam um tempo considerável para serem executadas. Em muitos casos, uma contagem precisa não é necessária – uma estimativa aproximada será suficiente. Nesses casos, use a função `APPROX_COUNT_DISTINCT`, conforme mostrado no seguinte exemplo:

SQL

```
SELECT dates.CalendarYear AS CalendarYear,
    APPROX_COUNT_DISTINCT(sales.OrderNumber) AS ApproxOrders
FROM FactSales AS sales
JOIN DimDate AS dates ON sales.OrderDateKey = dates.DateKey
GROUP BY dates.CalendarYear
ORDER BY CalendarYear;
```

A função `APPROX_COUNT_DISTINCT` usa um algoritmo _HyperLogLog_ para recuperar uma contagem aproximada. É garantido que o resultado tenha uma taxa de erro máxima de 2% com 97% probabilidade, portanto, os resultados dessa consulta podem ser semelhantes à tabela a seguir:

|CalendarYear|ApproxOrders|
|---|---|
|2023|235552|
|2024|290436|
|2025|304633|
|...|...|

As contagens são menos exatas, mas ainda são suficientes para uma comparação aproximada das vendas anuais. Com um grande volume de dados, a consulta que usa a função `APPROX_COUNT_DISTINCT` é concluída mais rapidamente e a exatidão reduzida pode ser uma compensação aceitável durante a exploração básica de dados.

> [!Observação]
> 
> 
> Consulte a documentação da função [APPROX_COUNT_DISTINCT](https://learn.microsoft.com/pt-br/sql/t-sql/functions/approx-count-distinct-transact-sql) para obter mais detalhes.
